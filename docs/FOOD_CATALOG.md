# AI 食品基础库

本次按用户要求，调用服务器现有 `Qwen3.8-27B`，一次性分批扩充食品基础库。数据用于日常饮食记录，来源为模型估算，未经实验或权威成分表核验。不得把数据来源写成 USDA、食物成分表实测或营养标签。

## 数据口径和范围

- 所有条目统一为每 **100 克可食部**，能量单位 kcal，蛋白质、脂肪、碳水化合物单位 g。饮品也以重量 100 克记录，不混用毫升。
- 单独记录生鲜、煮熟、蒸熟、炒熟、煎熟、烤熟、炸熟、炖熟、干制、即食、饮用、烘焙状态。
- 生成主题覆盖 72 类：谷物与主食、薯芋豆类、蔬菜菌菇、水果坚果、肉蛋水产、乳制品、家常菜与小吃、快餐、零食、甜品、饮品和调味品。
- 每个主题要求约 30 条候选；交叉重复、非法结构、数值异常会减少最终入库量，最终统计以数据库和导出清单为准。
- 复合菜使用常见做法的估算，配料、含水量、用油和糖量变化会影响实际值。

100 克可食部是食品成分数据常见报告口径，参考 [FAO 食品成分数据说明](https://www.fao.org/4/y4705e/y4705e14.htm)。该口径不代表本库的模型数值已获 FAO 验证。[USDA 的食品说明文档](https://fdc.nal.usda.gov/Foundation_Foods_Documentation/)也强调区分原料和加工状态；本次没有导入 USDA 的实测数值。

## 数据存储

数据库仍为 `ai_nutritionist_h5`：

- `foods`：现有计算所需的食品编码、名称、能量、三大营养素。
- `food_metadata`：一对一存储分类、生熟状态、别名、来源类型、模型、生成批次、100 克口径和核验状态。模型条目为 `source_type=ai_estimate`、`verified=0`。
- `food_import_batches`：生成配置、模型、进度、重复数、拒绝数和完成状态。

原有 10 条演示数据及其编码保留，来源显示为演示数据；不覆盖历史餐食和已保存营养计算结果。新增编码由规范化名称确定，重复执行不会覆盖已有食品。

审计文件放在服务器 `/data_1/ai-nutritionist-h5/data/food_catalog/qwen-foods-20261016/`：

- `foods_before.json`：扩充前的食品快照。
- `NNN-response.json`：原始模型响应及模型返回的用量信息，不包含服务密钥。
- `NNN.json`：每个主题的候选，保留以便断点复跑。
- `NNN-rejected.json`：未通过校验的候选及原因。
- `progress.json`：本次生成进度。
- `catalog.json`、`catalog.csv`、`summary.json`：从最终数据库导出的完整食品、来源和分类统计。

## 校验与匹配

入库前校验名称、别名结构、单位、生熟状态、有限数值、非负值、单种宏量营养素不超过 100g、宏量总量以及能量与宏量营养素的粗略一致性。这些检查只能发现明显异常，不能确认每条数值准确。

按规范化名称去重，保留生熟差异。识图后优先匹配完整名称和明确别名，避免把很短的子串随意匹配为不同菜品；多个同等候选无法确定时，留给用户手动选择。前端支持名称、别名和分类搜索，每次最多展示 60 个选项，同时保留当前选中项，防止大量选项拖慢手机页面。

## 执行与导出

模型和数据库密钥继续从服务器 `.env` 读取，不写入脚本。以下命令会操作共享食品库，须在了解范围后执行：

```bash
cd /data_1/ai-nutritionist-h5
# 相同批次使用缓存响应继续；--apply 明确启用入库
sudo docker-compose run --rm --no-deps api python -m app.seed_food_catalog \
  --apply --batch-id=qwen-foods-20261016 --count=30 --concurrency=4 --max-tokens=6000

# 从数据库重新导出最终清单
sudo docker-compose exec -T api python -m app.export_food_catalog --batch-id=qwen-foods-20261016

# 查看此次生成日志
tail -40 deploy/food-import.log
```

这是一轮按需导入，没有创建周期性自动任务。脚本支持缓存复跑；新增真实核验数据时应使用独立来源和核验标记，避免把模型估算误标为已核验。
