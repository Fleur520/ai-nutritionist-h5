# SQLite 数据迁移到 MySQL

本版本只使用 MySQL。已有 MySQL 部署无需导入；保留其原有连接和数据。旧版 `APP_DB_ENGINE=sqlite` 会被拒绝；如果发现旧 SQLite 文件且未显式选择 MySQL，启动也会失败，避免误以为空库是原用户数据。

迁移工具是一次性的人工操作，不随应用启动或部署自动执行。它以只读方式打开 SQLite，对一个**已创建且没有任何表的独立 MySQL 库**建表并导入，逐行核对每个字段。它不会删除、修改源库或清空目标库。表、字段不在本版本支持范围时会停止；不要绕过检查。照片文件、`.env`、食品生成审计文件不包含在数据库导入中，也不能提交到 Git。

1. 安排停机，停止旧应用的所有写入；备份 SQLite 主文件及其 WAL/SHM（如有）、图片目录、食品目录审计文件和服务端 `.env`，并验证备份可恢复。确保迁移期间没有其他进程写源库。
2. 在 MySQL 创建一个新的空数据库和有足够权限的专用账号。不要使用当前应用库或有任何数据的数据库。备份目标服务配置。为迁移进程提供 `APP_DB_ENGINE=mysql`、`MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE` 等配置；密钥只放在受限的服务端环境，不写入命令历史。
3. 在 `backend` 目录安装锁定依赖后执行：

   ```bash
   python -m app.migrate_sqlite --source /path/to/backup/nutrition.db --target <MYSQL_DATABASE的实际值>
   ```

   `--target` 必须与配置中的 `MYSQL_DATABASE` 完全一致。源应是包含完整 WAL 状态的可恢复副本，不能只复制正在写入的主文件。
4. 检查各表核对数量，独立抽查登录、档案、餐食、聊天、营养报告及食品来源字段。数据库图片字节会迁移；文件图片必须在新环境保持原路径可访问，并确认 `APP_MEDIA_DIR` 指向正确目录。核对图片权限及鉴权。先在隔离候选环境完成这些检查，再依据发布流程切换配置。
5. 只有合并的 `main` 提交通过指定的 `ci.yml`、且发布验收通过后才可激活版本。保留旧镜像、原 `.env`、SQLite 备份和图片备份。切换失败时恢复旧配置和旧镜像。新 MySQL 一旦接受写入，其新增数据不会自动回写 SQLite；回退前必须停写并备份、人工核对和处理这些增量，避免丢失数据。

MySQL DDL 会自动提交。若导入失败，数据事务回滚但目标可能留下空表；工具不会自动清理。请检查原因，使用另一个新建的空库重试。不要对原库执行清理命令。工具拒绝 SQLite 视图、触发器、未识别的表或额外列，以防静默丢失数据；这类情况需要针对实际结构编写并验证迁移。

测试使用隔离的 `test_` 数据库。MySQL 5.7 由 CI 验证；本地也可使用兼容版本，但不得把测试指向业务库。
