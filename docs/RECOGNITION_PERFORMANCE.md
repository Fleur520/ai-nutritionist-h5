# 餐图识别：准确度、模型配置和并发验收

验收目标：10 个用户同时请求，所有请求正常返回，P95 不超过 20 秒；不确定的食品允许人工确认。计时包含上传和识别，不用重复图片的业务结果缓存代替实际推理。

## 当前基线和测量口径

2026-10-18 的原配置单用户耗时 18.539 秒；10 路同时识别全部成功，P50 73.003 秒、P95 137.087 秒，没有请求在 20 秒内结束。原配置测试反复使用同一真实餐图；下游模型缓存可能已经预热。

独立餐图实例关闭思考、增加调度容量后，首轮 10 路 P95 为 23.263 秒，另一轮 22.164 秒。尚未达到目标。新增提示词的两轮结果分别为 31.226 和 22.398 秒，不能仅挑最快一次宣称通过。

新负载使用轻微曝光变化产生不同视觉内容，避免完全相同图像的编码缓存命中；这些变体仍来自同一个场景，不能当作独立图片来计算整体识别准确率。明确区分正确识别、自动编码匹配和人工待确认，不能把自动填满率当作准确率。

显式FP8候选单路为7.577秒、十路P95为20.245秒；随后将上传图片的解码、EXIF校正、缩放和JPEG编码放入受限线程池（默认最多4路），保留原有格式和像素限制，并在取消时等待编码结束、清理本次文件。该版本十路P95为19.047秒，10/10在20秒内完成。

准确提交`47b9249`的干净API/Web镜像连续5批、每批10路的50请求验证通过：50/50成功，P50 **18.822秒**、P95 **19.101秒**、最大**19.182秒**，50个请求均在20秒内完成。50个图像字节哈希均不同，业务结果缓存未启用；测试账号和照片全部清理。该测试只证明这一餐图变体负载的承载结果，不能保证任意尺寸、复杂度、上游负载下的固定响应时间。

准确度检查：这50个输入中的酸奶、米饭、紫薯均被50/50次识别；这只是同一场景稳定性，不能宣称整体准确率100%。另一张原有烧烤图的独立工作流调用为4.133秒，返回虾、薯条、玉米、土豆；具体烹调方式无法确认的项目保留人工选择。真实餐图手机端单次回归为5.253秒，包装100克酸奶按100克返回，食品编码及原始文档证据均经实时数据库核对。修改重量、切换食品、确认候选并保存6项共1304 kcal与数据库一致。所有重量和复杂菜品仍需用户确认。

## 保留平台后的追加优化与复验

用户要求保留现有BiSheng平台，本轮不安装图片输入补丁，不改工作流655、文档库202、模型配置或服务器`.env`。补丁开关继续关闭。

追加回归发现原2048像素方案仍有波动：在新的曝光变体上，30/30成功，但P50为21.912秒、P95为29.859秒、最大29.910秒，仅7次在20秒内完成。工作流内部调用耗时占主要部分。这组结果也必须保留，上一轮19.101秒不能当作任意图片或时段的保证。

当前应用提交`fafce27`将**新上传图片长边上限改为1536像素**，按比例缩放，先校正方向，不放大小图；同宽高比下，最大像素量比2048方案少约44%。已保存的照片不会改写。`APP_IMAGE_MAX_EDGE`可配置为768～2048，默认1536；`APP_MAX_IMAGE_CONCURRENCY`仍默认4。

该准确提交连续5批、每批10个独立用户的50请求复验：**50/50成功，P50=16.729秒、P95=17.064秒、最大17.643秒，50次均在20秒内完成**。计时含上传；50个输入字节哈希不同，所有响应`coalesced=false`，没有业务结果缓存。前30个输入与本轮2048方案的曝光变体一致，随后再扩展20个输入；完整50次均计入统计。

同一用户同时识别同一上传ID时，现在仅共享正在进行的识别任务。1536方案的10个重复请求中9个被合并，10/10成功、P95=5.834秒；随后单独重新识别`coalesced=false`，耗时5.282秒。**此项5.8秒不是10个独立用户的并发成绩**。任务完成或失败后立即移除，不缓存已完成结果；每个响应仍用当前数据库复核食品编码。合并不跨用户或不同上传ID，目前仅在单API进程内生效。

取消一个等待者不会影响其他请求，全部等待者退出则取消上游并等待其清理；正在清理的任务不接受新共享请求。注册表容量与AI并发上限一致，超量请求返回429。上传线程即使连续收到取消也会保留编码名额，完成后只删除本次文件，防止迟写残留。

1536真实餐图手机端单次5.259秒，自动映射5/7项，返回真实文档库202的来源和哈希；不确定的食物继续人工确认。390像素视口无横向溢出，重量、食品切换、候选确认和保存6项1264 kcal均与数据库一致。50个曝光变体中，酸奶/发酵乳、米饭、紫薯均出现；仍只证明这一个餐盘场景的稳定性，不能据此计算整体识别准确率。小包装文字和复杂菜品需核对，1536与2048可按后续多场景评测取舍。

验证包含223项SQLite测试、223项隔离`test_` MySQL测试、47项发布回滚测试、25项前端检查及生产/镜像构建。横竖图、方向、禁止放大、重复请求隔离、容量、取消、失败重试和关闭清理均有回归覆盖。压测及手机验证的临时用户、餐食和照片按身份校验清理，食品库2060项及其快照保留。代码经[PR #10](https://github.com/Fleur520/ai-nutritionist-h5/pull/10)交付，合并后的准确提交仍须通过`ci.yml`及发布验收才可激活。

## 实际模型配置

| 服务 | `172.16.10.3:9000` | `172.16.10.3:19000` |
| 名称 | `Qwen3.8-27B` | `Qwen3.8-27B-Food` |
| vLLM | 0.27.1 | 0.27.1 |
| GPU | L20 0–3，4卡TP | L20 4–7，4卡TP |

| 同时推理序列 | 4 | 16 |
| 上下文 | 65536 | 8192 |
| 批次token预算 | 16384 | 16384 |

原目录及容器名带FP8，但检查实际权重张量、模型配置和引擎日志均为BF16。不能仅凭命名判断量化是否生效。专用实例使用 [docker-compose.vision.yml](../deploy/docker-compose.vision.yml)，读取服务器私有环境中的密钥；原模型与服务器`.env`保留。

## 已定位的额外开销

H5 侧数据库读取约70–270ms，食品复核约12–72ms。`/api/meals/recognize`的`timings_ms`细分准入、图片上传、各轮工作流调用、协议校验、食品库和匹配耗时，不记录图片、密钥或用户标识。

BiSheng 1.3.1 的图片表单即使设置`file_content_size=0`，仍调用文档解析/OCR，并将文字写入临时向量库；餐图识别实际只引用`meal_image_files`，不使用这些临时文本。

[patch_bisheng_image_input.py](../deploy/patch_bisheng_image_input.py)只生成补丁副本，不编辑安装源。补丁仅在输入同时满足`skip_image_text_extraction=true`、`file_type=image`、文本长度为0时直传经过校验的图片，保留原生文件上传、路径及来源。其他配置保留原文档处理逻辑。工作流生成器的`--image-only-input`默认关闭，必须先在实际BiSheng版本部署补丁并通过原生上传和回滚验证后才能开启。

## 可重复压测

在独立候选API容器中使用 [benchmark_recognition.py](../deploy/benchmark_recognition.py)。脚本强制连接`test_`开头的MySQL数据库，通过该测试项目自己的`http://web`访问Nginx；创建每路临时用户、上传私有图片、实际调用工作流，最后按身份校验清理用户、餐食和图片。清理失败会保留私有账本并报错。结果、账本及图片不得提交。

```sh
PYTHONPATH=/app python /audit/benchmark_recognition.py \
  --label final-candidate --concurrency 10 --rounds 5 --vary-images \
  --image /private/meal.jpg --report /private/final-c10.json
```

P95采用全部完成请求的最近秩统计，慢请求或错误不从统计中剔除。正式验收需要足够请求量、完整测试结果，以及相应提交的CI和发布验收；单次十路试跑只用于定位瓶颈。

## 部署与回退

独立模型和独立测试工作流先验收；原工作流652及通用模型43保留。代码通过专用分支PR交付，合并提交的`ci.yml`成功后才允许部署。上线需再次核对工作流版本、模型路由、文档库快照、下拉反显、人工确认与营养保存，发布验收失败恢复上一版应用镜像。平台补丁和模型服务的回退需要分别保留原源文件/镜像及原配置，不把应用回滚当作它们已自动回滚。
